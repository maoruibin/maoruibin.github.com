## 先说这篇要讲什么

不讲理论，不讲宏大叙事。

只讲我这一年、每天真在用的东西。

分四块：用 AI 查东西，把重复的活儿封装成一句话，真正用 AI 写代码，最后聊一个我觉得更值钱的方向。

前三块是技巧，是我每天省时间靠的东西。

但写到最后我越想越觉得，技巧只是皮。真正的大变化在底下，是潮流。

## 一、小龙虾：手机上就能查代码

先说个最轻的。

中午吃饭，领导在群里抛了个问题：analysis_extra 上报的到底是父评论的字段，还是评论自己的？

按以前，这事儿得吃完饭、回工位、打开 Android Studio、搜代码、看逻辑，来回半小时。

那天我没等。

直接在钉钉里给小龙虾发了张 JSON 截图，加一段语音把问题说了一遍——还挺啰嗦的。

它自己去翻了代码，找到 getReadLogExtraInfo() 的实现，给了结论，还附了证据。

结论是：每条评论用自己的 analysis_extra，不是父评论的。JsonComment 和 Status 各自实现了 ITimeRecordStatistics 接口，各返回各的字段。

两分钟搞定。

这件事打破了一个我以前觉得理所当然的限制：查代码，必须在电脑前。

现在不用了。地铁上、吃饭时、开会走神的间隙，掏出手机就能查。

而且小龙虾不止能查代码。

产品经理用它查别的模块的逻辑，后端同事用它翻接口，我自己还用它把一堆截图整理成文档和 PPT。

它本质是个能读微博代码、能读文档、还懂上下文的 Agent。查代码、查文档、整理成材料，它都干得比手动好。

## 二、Skill：把重复的活儿封装成一句话

查是第一步。

再进一步，是把你反复在做的事，封装成一句话。

这就要说到 Skill。

Skill 说白了，就是一份 Markdown 说明书，加一两个脚本。你把一件事怎么做告诉 AI，它以后一句话就能帮你从头串到尾。

举两个我每天都在用的。

### 一句话同步多仓库

微博是多仓库发版，壳工程加几十个子模块。

日常开发有个烦人的事：同步代码。漏拉一个模块，或者远程分支变了没跟上，编译就报错。

以前每次得挨个 cd 进去 git pull，繁琐，还容易漏。

我写了个 Skill，叫 weibo-sync-modules。

它会自动识别项目根目录，解析 settings.gradle 里所有活跃的模块，智能处理多仓库的映射（比如两个模块名指向同一个 git 仓库，就只 pull 一次），然后逐个 git pull --rebase。

现在我说一句"同步模块"，所有模块自动拉最新，结果列成一张表给我看。

（说句实话，这事儿用 shell 脚本也能干。但 Skill 的好处是，AI 理解项目结构，我不用维护一堆 if else。）

### 上传 APK 到 OTA：2018 年和 2026 年

再说个更有故事的。

给产品、测试验收，经常要传一个临时开发包到 OTA 平台（ota.client.weibo.cn）。流程很烦：开浏览器、登录、填版本号、填描述、选文件、上传、等、复制链接发人。

2018 年的时候，我被这事儿烦透了。

抓包分析了 OTA 的上传接口，写了一个 Android Studio 插件，在 IDE 里直接传。

当时花了大量时间：抓包、分析协议、写插件 UI、适配各种 IDE 版本。维护成本极高。

2026 年，同样的事，我写了个 Skill 就搞定了。

一个 SKILL.md，加一个 upload_apk.sh。

它干什么：从 git 分支名生成版本号，从最近一条 commit message 生成描述（英文自动翻成中文），检查 APK 在不在、显示大小，调 OTA 接口上传，存历史记录，最后把下载链接甩给我。

我说一句"上传包"，全干完。

**同样的问题，2018 年写插件要折腾两周，2026 年写 Skill 只要半天，维护成本还低一个数量级。**

接口变了？改几行 curl。Cookie 过期？换一个文件。不用重新编译，不用适配 IDE 版本。

这就是 Skill 的价值：把重复劳动变成一句话，AI 帮你扛掉那些维护的脏活。

## 三、Codex：真正用 AI 写代码

前两块还在"省事"的层面。

真正的大块时间，是写代码。

这一块我想重点说 Codex。

先交代背景。公司内部大家现在用的是 WeCode，它其实是 Claude Code 的一个包装。VS Code 也封装了 Codex。

但我自己，推荐桌面版 Codex。

为什么不是命令行、也不是 VS Code 里的封装，而是桌面版？

一个最直接的理由：会话管理。

桌面版是可视化的、项目级别的。我能一眼看到自己开了哪几个项目、每个项目里有哪些对话、谁分叉了谁、谁是谁的延续。

终端里跑 Claude Code 也很强，但说实话，可视化之后，那种"我到底在哪个会话里"的混乱感没了。

还有一个感受，可能有点玄：同一个模型，在 Codex 桌面版里，它显得更聪明。

我猜是因为它的上下文管理做得好——会话怎么分叉、记忆怎么带，这些细节叠起来，最后呈现出来的就是"它更懂我现在在干嘛"。

### 几个我离不开的功能

Fork（分叉）。一个对话聊到一半，我想试另一个方向，不用开新窗口重打背景，直接 Fork 一份，两条路并行着走。

批注。AI 给的方案里某一段，我想单独圈出来补充要求、或者标个疑问，直接在那段上批注，它只针对那一段改。

侧边聊天。可以同时开两个窗口，一个主战场写代码，一个侧边问问题、查东西，互不打扰。

全局记忆。项目级别的偏好、约定，它都记着，不用每次重复交代。

侧边面板。能直接打开浏览器、看文档，不用在几个窗口之间切来切去。

说白了，终端里能干的事，桌面版基本都能干，但用着就是更舒服。

### 实战：开发正文页的点击预加载

光说功能没意思，讲个我最近怎么用它干活的。

需求是这样的：微博正文页要做点击预加载——你点 Feed 之前，请求就先打出去了，点进去直接出内容，不用等。

整个开发我都是在 Codex 里做的。（用 VS Code 加 Codex 也几乎一样，但 Codex 桌面版的可视化体验更顺。）

第一步，给上下文。

这是老操作了。我让它先读正文页的流程文档，搞清楚整个数据是怎么流的。我们之前写的那些文档，这时候就起作用了。

第二步，让它想方案。

核心难点是把正文页的请求，挪到 Pre-fetch 流里去，参数得对上。我让它自己设计，怎么挪、挪哪些参数。

第三步，调试验证。

我是这么干的：让它先在点击时发一个请求，点进正文页再发一个一样的，然后把两个的参数和日志都打出来。

第四步，让它自己改。

我把正确请求的日志贴给它，让它对比——它自己设计方案的日志、正确接口的请求参数、以及响应数据。

让它自己看哪里不对，自己改。

这一步我觉得特别关键，也是我觉得用 AI 最好的姿势：

**让 AI 加日志，让 AI 对比日志，让 AI 出方案。**

人只负责给出"什么是对的"——一份正确请求的真实日志。剩下的对比、定位、改方案，它比人快，也比人细。

这个思路，比"AI 写一段我 review 一段"好用太多。

### 数据分析也能丢给它

顺带一提，不只是写代码。

正文页的数据分析我也丢给它。我把数据喂进去，它分析、总结，最后直接写进钉钉表格。

以前这种活儿得开 Metabase、导表、写 SQL、整理，一下午。现在几轮对话的事。

## 四、真正的大红利：让系统面向 Agent

前三块讲完，听着都是我个人的小技巧。

但这一年用下来，我有个越来越强的感受。

我们这些技巧，说到底都是局部优化。

因为有一个更大的东西没动：我们的系统，根本没围绕 AI 重新设计，甚至没怎么适配 AI。

你想想公司内部的系统——Packer（崩溃异常）、AB 平台、Kibana、Metabase、配置平台。

它们全是给人看的。

人去点，人去查，人去填。

但现在，干这些活，AI 明显比人干得好。查数据、写周报、建配置、看异常，让 Agent 来做，又快又准。

问题是，这些系统没给 Agent 开门。

### 我想做的一件事

说个具体的。

Packer 是公司的崩溃异常系统，Alpha、Release、线上各阶段的崩溃都收。架构组其实做了 AI 工具能看线上异常，但业务这边很难用起来。

我最近一直在想一个事。

写一个智能体，定时去 Packer 拉崩溃堆栈和版本信息。

拉回来之后，让 Agent 分析。

因为现在的 Agent 能读 Android、iOS 的代码，还能读文档，它可以围绕一个堆栈生成一份真报告。

更关键的是，小龙虾会把最近的 Gerrit 提交都记着。Agent 能根据崩溃首次出现的时间，回到那个版本的代码里去定位，对这次崩溃做前置判断，甚至预测。

这件事对人来说是重复劳动——每次崩溃都这么查一遍。

对 AI 来说，太简单了。

那我做一个定时任务，每天或每周跑一次，分析完把报告发到群里，@ 对应的人。

这不比人盯着看有价值多了？

但前提是，Packer 得给我一个 API。

### 外面已经在这么干了

这不是我一个人在这儿瞎想。

看几个信号。

微博自己最近干了一件事：把微博的发布流程做成了一套 CLI。你授权一下、装个 CLI，就能用命令行发微博、看微博、发评论。

这是干嘛？这就是在面向 Agent 开放。

钉钉的新 CEO 上任，发了五条声明，最后一条是：让钉钉所有内部的工具系统，都要易于被 Agent 使用。

腾讯的 QQ，最近也做了一个专门给 AI Agent 用的工具，让 Agent 能收发邮件，实现 Agent 之间的通信。

这些事凑在一起，信号特别明显。

**下一个用户不是人，是 Agent。系统得给它开门。**

### 退一步：你不开放，我也有土办法

当然，理想是系统都开放 API。现实是，大多数还没开放。

但不开放，不代表干不了。

我自己就这么干过。建 AB 配置项，走界面填一堆东西太麻烦，我抓了个接口，做成 Skill。现在一行命令，配置项、版本号全填好。

有接口，Agent 就能用。

没有接口，我抓一个出来也能用。

但如果 AB 平台能原生支持 API，一个 token 鉴权就搞定，那是不是更好？

### 其实 Packer 这事，已经通了

说回 Packer。

我最近找做 Packer 的客户端同学聊了聊，提了开放 API 的需求。

结果出乎意料——他们态度特别积极，很快就支持了。现在接口已经能用了，我的崩溃分析智能体可以真正跑起来。

但说实话，这是运气好。

Packer 顺，是因为做它的同学就在身边，沟通成本低，他们也认可这个方向。

换个系统就不一定了。你给别的团队提这种需求，流程长、排期慢，能不能推得动都不好说。

这也是我想借这次分享说的一点：别等。你手里有 Agent，缺的是接口；接口拿不到，就先抓一个出来。先让事情跑起来，比什么都重要。

### 这是潮流

我觉得未来一定是这样：系统之间，不管是业务还是内部的，都在面向 Agent 开放。

谁先开放，谁先吃到红利。

因为 Agent 现在就有，Codex、小龙虾、Claude Code、公司自己的 Agent，都是现成能干活的。工具都备齐了，就差系统给它们递个接口。

这就是我说的，技巧是皮，潮流是骨。

## 写在最后

前面那些技巧——小龙虾查代码、Skill 封装、Codex 写代码——你拿去就能用，今天看完明天就能省时间。

但如果只记一件事，我希望是最后这块。

别只想着怎么把 AI 用得更好。

也要想着，我们手上的系统，怎么才能让 AI 用得更好。

Packer 的 API 已经通了，崩溃分析的智能体我会先跑起来。跑通之后，我再把这套思路往别的系统上推——哪怕得自己抓接口。

如果你也觉得这个方向对，来找我，我们一起推。
